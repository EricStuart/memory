# Kele 主项目开发经验

英文完整记录：[../kele.md](../kele.md)

## 主要主题

### 支付与计费

- 个人计费页隐藏支付方式选择器时，仍需保留支付状态、订单创建、支付弹窗、待支付订单恢复和接口契约。
- 默认支付渠道应在状态和订单 payload 中明确设为支付宝，不能只修改显示层。
- 简化计费 UI 时，测试应同时断言“选择器不可见”和“确认支付流程仍然存在”。
- 生产支付需要订单幂等、金额和商户身份校验、主动查询/关闭订单以及权益发放的事务一致性。

### 文本与工作流

- 润色文本中的 `日本腔调/疑惑` 等交付标签不能只依赖提示词；模型输出后还要做确定性恢复，并验证数据库和浏览器展示结果。
- 自动工作流的诊断要从任务/API-step 的原始输出开始，沿着规范化、持久化、read model 和 UI 逐层确认，不能只看画布汇总状态。
- `next.internal` 只允许在可信内部请求边界执行，同时仍需项目访问校验和内部请求头。
- 脚本分析、场景拆分、镜头拆分应分别记录输入、执行器、落库表和读取端，避免把读缓存问题误判为生成失败。

### 个人登录边界

- 工作区成员的禁用状态属于工作区范围，不能写回共享用户状态并影响个人门户登录。
- 个人认证应先查个人账户边界，再映射个人账户禁用错误；修复必须配套契约测试和真实登录验证。
- 已确认根因但未完成修复的记录必须标注“未验证”，不能当作已部署结论。

### Git 与运行维护

- Git 提交作者（`user.name`/`user.email`）和 HTTP 推送认证是两套状态，切换账号时先分别确认。
- HTTP 认证失败通常先清理实际 remote 主机对应的 Credential Manager 条目，再使用非交互式 fetch/rebase/push。
- 提交前只暂存目标文件；远程推进后重新 fetch、rebase，并用 `HEAD...origin/main = 0 0` 和干净工作区收尾。
- Windows 本地运行要验证 Web、Gateway、NATS、PostgreSQL、PostgREST 和工作流后台进程，不应只检查一个 HTTP 端口。
